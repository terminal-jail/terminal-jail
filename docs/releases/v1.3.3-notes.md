terminal-jail v1.3.3 — patch: wheel-install bridge interpreter + release-mode installs

## Fixed

- **Wheel installs run the bridge on the installing interpreter
  (`TJ-DF-061`).** A pip-installed wheel's console script runs under the
  installing interpreter, but an unactivated venv puts no `python3` on
  `PATH`. The wrapper's bridge path — module discovery, bridge execution,
  command JSON encode, verdict parse, modify extract, warn-reason extract —
  resolved bare `python3`, so every firewall-on invocation from such an
  install failed closed (`[bridge-error]`, or
  `interruptor-bridge-unavailable` exit 126 when `python3` was absent
  entirely) and the shipped rule catalog never evaluated. `cli.py` now
  exports the installing `sys.executable` as `TERMINAL_JAIL_PYTHON` (only
  when unset, so an operator override still wins) and the `standalone/terminal-jail`
  bridge path runs under `${TERMINAL_JAIL_PYTHON:-python3}`. An explicitly
  set but nonexistent interpreter still fails loudly at exit 126 — no silent
  fallback. The seccomp/Landlock loader trampolines are deliberately
  unchanged; they are not the bridge path.
- **Release-mode installs match the published assets (`TJ-DF-062`).**
  `install.sh` release mode now downloads the published wheel plus its
  `SHA256SUMS` manifest instead of a checkout-only path, and its
  `TERMINAL_JAIL_VERSION` default moves to the newest release that actually
  has downloadable assets. `README.md`, `docs/quickstart.md` and
  `plugin/test_install.py` follow the same story, so the documented install
  and the tested install no longer disagree.

## Carried forward (known, not fixed here)

- **`RELCI-001` — the tag-triggered Release workflow still cannot publish on
  its own.** The `Preflight — verify the token may create releases` step
  fails because the repository's Actions workflow-permission default caps
  `permissions: contents: write`; `gh api repos/terminal-jail/terminal-jail
  --jq .permissions.push` reports `false` for `GITHUB_TOKEN`, so
  `gh release create` would be refused. Reproduced twice for this tag: the
  tag-push run `42774392420` and a `workflow_dispatch` run `42778106840`
  (`-f tag="v1.3.3"`) both fail at that preflight, so the dispatch path is
  not a workaround. The v1.3.3 artifacts were therefore built from the tagged
  tree and published by hand with the recipe in `docs/releasing.md` step 5b,
  exactly as v1.3.1 was. Owner/app-admin setting:
  Settings → Actions → General → Workflow permissions.

## Known residual (measured, not fixed here)

- **`TJ-DF-061` is a partial fix: the in-jail loader trampoline stage still
  resolves bare `python3`.** The bridge path is fixed, but with a wheel
  install and no `python3` on `PATH` the run now evaluates correctly and then
  still fails at exit 127 when the Landlock/seccomp trampoline is spliced in
  (`plugin/terminal_jail/_bundled/terminal-jail` lines 1384-1398, 1426,
  1465-1487 hardcode `python3`; only `_TJ_BRIDGE_PY` on line 279 honors
  `TERMINAL_JAIL_PYTHON`). Measured two-arm: v1.3.2 exits 126 with no verdict
  (bridge broken), v1.3.3 emits `{"event":"verdict","action":"allow","layer":"engine"}`
  and exits 0 on a normal `PATH`, but exits 127 with the command unevaluated
  when a broken `python3` shadows the installing interpreter. Filed as a
  follow-up row rather than blocking this patch.
