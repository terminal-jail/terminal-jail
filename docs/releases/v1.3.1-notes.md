terminal-jail v1.3.1 — patch: complete pip-wheel installs

## Fixed

- **Complete pip-wheel installs (`RELPKG-001`).** A built wheel shipped only
  the library: no `terminal-jail` command and an inert Landlock tier (the
  interruptor could not find `landlock-loader.py`). The wheel now declares a
  `terminal-jail` console script (`terminal_jail.cli:main`), ships the
  standalone bash CLI and the three tier loaders byte-identically as package
  data (`terminal_jail/_bundled/`), exports `TERMINAL_JAIL_VERSION` from
  importlib.metadata, points the wrapper's loader/bridge overrides at the
  shipped copies when unset, and `loader_path()` (fs + net) falls back to the
  bundled copy after the repository walk — so installing a wheel yields a
  working command and live containment tiers.

## Why this patch exists

v1.3.0's assets were built from `be643a8`, *before* that packaging fix landed
(`4843ffb`), so the v1.3.0 wheel users download is the library-only artifact.
If you installed terminal-jail from the v1.3.0 wheel, upgrade to v1.3.1:
`pip install --upgrade terminal_jail-1.3.1-py3-none-any.whl`.

PyPI remains a non-channel ([docs/supply-chain.md](https://github.com/terminal-jail/terminal-jail/blob/main/docs/supply-chain.md));
GitHub Releases is the artifact channel.

## Carried forward (known, not fixed here)

- **`RELCI-001` — the tag-triggered Release workflow cannot publish on its
  own.** Its `Preflight — verify the token may create releases` step fails
  because the repository's Actions workflow-permission default caps
  `permissions: contents: write`, so `GITHUB_TOKEN` lacks push and
  `gh release create` would be refused (observed on the v1.3.0 tag run
  `41743401719`). The v1.3.1 artifacts were therefore built and published by
  hand from the tagged tree with the identical recipe documented in
  `docs/releasing.md` step 5b. Owner/app-admin setting:
  Settings → Actions → General → Workflow permissions.
